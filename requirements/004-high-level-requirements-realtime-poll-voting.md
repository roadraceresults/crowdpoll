# OVERVIEW
We are creating a real-time opinion poll system that allows users to vote on various polls and see the results in real-time.   
This system will replace the `SIMPLE WEB APP CLIENT` that exists in this project.
The system will be built using TypeScript and will serve the polls via HTTP on the port specified in the environment variable `APP_PORT`.   
The polls will be stored in a MongoDB database, and each poll will be identified by a unique number `PID`.  
The name of the mongoDB database will be specified in the environment variable `APP_MONGODB_NAME` (default "app01").  
The connection string for the mongoDB database will be specified in the environment variable `APP_MONGODB_URI`.  

# POLL CONFIGURATION
`PID`: a unique identifier for each poll, generated by the system at creation time.  
`Title/Question`  (up to 100 characters, can be multiline)  
`SubTitle`  (optional, up to 100 characters, can be multiline)  

- `ChoiceLabel` 1  (up to 100 characters, single line)
- `ChoiceLabel` 2  (up to 100 characters, single line)
- ...  
	(with no less than 2 choices and no more than 50 Choices)  

`VoterCountLimit` (default to 500)  
`InvitedVoterList` (limited to 500 entries)  
- `InvitedEmailAddress` (limited to 200 characters)
   
`BannedVoterList`
`BannedEmailAddress` (limited to 200 characters)

`ChoiceMode` can be either:  
1. `SINGLE-CHOICE-POLL` (default)  
2. `MULTIPLE-CHOICE-POLL`  

`ResultsVisibility` can be either:  
1. `ANONYMOUS-POLL` where the name of the poll participants are not included in the results (default)  
2. `TRANSPARENT-POLL` where the choice(s) of each user are included in the results  

`VoteMutability` can be either:  
1. `FINAL-VOTE-POLL` where a user can not change their vote (default)  
2. `DYNAMIC-VOTE-POLL` where a user can change their vote  

`AccessMode` can be either:  
1. 	`PUBLIC_POLL` (default)  
	In this case, the poll can be viewed by:  
	- doing a search on the website  
	- being presented directly to the user as a suggested, relevant poll  
		(for example, on the Home Page that shows popular polls)  
	- clicking a link that navigates directly to the poll   

	Any user who is `Logged In` can also vote on the poll depending on whether the poll is a `DYNAMIC-VOTE-POLL` or a `FINAL-VOTE-POLL`, according to the logic describe below in the `POLL USER INTERFACE` section of these requirements.  
2) `PRIVATE_POLL_ANYONE_WITH_THE_LINK`  
	In this case, as the name suggests, if a user navigates to this poll, they can vote.    
	They must first be `Logged In` to vote, but they do not need to be on any list of invited users.
	The poll will not be displayed publically anywhere on the website.  
	This is a poll that a user can create and distribute the link however they choose.  
	Any user who is `Logged In` can vote on the poll depending on whether the poll is `DYNAMIC-VOTE-POLL` or a `FINAL-VOTE-POLL`, according to the logic describe below in the `POLL USER INTERFACE` section of these requirements.  
	This is the only poll type that makes use of the `VoterCountLimit`. As the name suggests, if the number of users who have voted on this poll is equal to `VoterCountLimit`, no other users will be permitted to vote. A message will be displayed to the user informing them that the poll has reached its maximum number of votes. 
	The main difference between a `PRIVATE_POLL_ANYONE_WITH_THE_LINK` and a `PUBLIC_POLL` is that a `PUBLIC_POLL` can be displayed to any user of the website, whereas a `PRIVATE_POLL_ANYONE_WITH_THE_LINK` will only be displayed to a user who navigates to the poll with a URL that has the correct `PID=` URL parameter. Also, the results of a `PUBLIC_POLL` will be displayed even if the user has not `Logged In`, whereas the results of a `PRIVATE_POLL_ANYONE_WITH_THE_LINK` will only be displayed to a user who has `Logged In`.  
3) `PRIVATE_POLL_INVITATION_ONLY`  
	In this case, part of the configuration for the poll, includes a list of emailAddresses in an `InvitedVoterList`.    
	The `InvitedVoterList` list is limited to 500 "Participants".    
	Each "Participant" is identified by `emailAddress`.  
	The record of votes for this poll will be pre-seeded with an entry for every "Participant" in the `InvitedVoterList`.  
	Each pre-seeded entry will initially have an empty list of selected `Choices` for the poll. i.e. "No Vote" has been cast.  
	The poll will be displayed to the user if their email address is validated against the `InvitedVoterList`.  
	Any user who is `Logged In` can also vote on the poll depending on whether the poll is a `DYNAMIC-VOTE-POLL` or a `FINAL-VOTE-POLL`, according to the logic describe below in the `POLL USER INTERFACE` section of these requirements.
	If the user navigates to this `PRIVATE_POLL` but their `emailAddress` does not appear in the `InvitedVoterList`, the user will be informed that they are not invited to vote in this poll. This will only happen if the URL of this poll has leaked, otherwise there is no way they would know the `PID` for the poll.  
	The user can navigate to this type of poll in 2 ways:
	- clicking a URL distributed to them 
	- the webapp may display this poll to them after `Log In` and their `emailAddress` is found in the `InvitedVoterList`  

	The main difference between a `PRIVATE_POLL_INVITATION_ONLY` and a `PRIVATE_POLL_ANYONE_WITH_THE_LINK` is that a `PRIVATE_POLL_INVITATION_ONLY` will only be displayed to the user if their `emailAddress` appears in the `InvitedVoterList`.				
  
`POLL_STATE` can be one of :  
- `PENDING-POLL-STATE`  
- `ACTIVE-POLL-STATE` (default)
- `CLOSED-POLL-STATE`
- `ARCHIVED-POLL-STATE` 

`START_DATE_TIME` and `END_DATE_TIME`:  
- a poll may have an optional `START_DATE_TIME` and an optional `END_DATE_TIME` that is displayed to the user.  
- the current date/time when the vote is submitted is compared against the `START_DATE_TIME` and `END_DATE_TIME`. 
- if the poll has not yet started, its `POLL_STATE` will be the set to `PENDING-POLL-STATE` and the user will be informed.
- if the `END_DATE_TIME` has past, its `POLL_STATE` will be set to `CLOSED-POLL-STATE` and the user will be informed.
- if the poll has a `START_DATE_TIME` and `END_DATE_TIME`, it will be displayed to the user in their local time zone as detected in the browser.
- the `START_DATE_TIME` and `END_DATE_TIME` will be stored in the database in UTC format.

### String Length Limits
When a Poll Configuration setting has a length limit, such as: `Title/Question`, `SubTitle`, `ChoiceLabel`, `InvitedEmailAddress`, `BannedEmailAddress` the system will enforce that limit by preventing the user from entering more than the allowed number of characters in the input field.  
When the user edits their profile to change `userName` the system will enforce the length limit by preventing the user from entering more than the allowed number of characters in the input field.  
In these cases, the system will also provide feedback to the user if they attempt to exceed the length limit of an input field.  
This length limit enforcement will be done client-side.

# INDIVIDUAL POLL USER INTERFACE
The UI/UX for the Poll has been implemented in the files in `./designDocs/pollUserInterface` .
`live-results.html`
`poll-card.css`
`poll-card.html`
`poll-card.js`
That implementation will be used in this implementation of the Poll WebApp User Interface.
In the pollUserInterface implementation, each poll is displayed in a `POLL-CARD` that renders the poll results on the front of the card and the voting interface on the back of the card.
  
After voting, the `Choice`(s) made by the user will be sent to the server and stored in the database.  
After voting, the results will include the user's current vote.   

The poll results displayed to the user will be updated as results change.  
This will be accomplished by polling an API endpoint on the server every 5 seconds to get the latest results for the poll. This polling interval is configured using an environment variable `APP_POLLING_INTERVAL` (default 5000 milliseconds).  

As described above, the poll can be `SINGLE-CHOICE-POLL` (exactly one selectable `Choice`) or `MULTIPLE-CHOICE-POLL` (one or more selectable `Choices`). For a `MULTIPLE-CHOICE-POLL`, the "vote count" for a choice MUST be the number of distinct participants whose current selection includes that choice; a percentage MUST be computed against the total number of selections made, so that the percentages of a `MULTIPLE-CHOICE-POLL` add up to 100 (apart from rounding); a `SINGLE-CHOICE-POLL`'s percentage is computed against the number of participants who have voted.

The results side of the `POLL-CARD` will display the total number of participants who have voted, and the total number of participants who have not yet voted if the poll is a `PRIVATE_POLL_INVITATION_ONLY`.  
The percentage for each choice will be computed against the total number of participants who have voted.

The user votes are stored in a MongoDB database.  
The environment variable `APP_MONGODB_URI` specifies the connection string for the MongoDB instance.  
Each `PID` (Poll ID) identifies a unique document in mongoDB.  
The JSON document includes the configuration as well as the record of votes.  
Each vote record will have a version timestamp so that if a user changes their vote there will be a chronological record of that.  
For a `SINGLE-CHOICE-POLL`, the most recent vote by a user is the one that "counts".   
For a `MULTIPLE-CHOICE-POLL`, the most recent vote by a user is the one that "counts", as well as all other votes with the same timestamp.  
  
This implies that when a user votes for multiple choices, the system will store all of those choices with the same timestamp. If the user `Submits` new `Choices`, the new set of choices will have a new timestamp, and the previous set of choices will be considered "overridden" by the new vote.  
  
This also implies that the voting UI for a `MULTIPLE-CHOICE-POLL` will allow the user to select multiple `Choices` and de-select a `Choice`.  The voting UI for a `SINGLE-CHOICE-POLL` will allow the user to select only one `Choice` which deselects any previously selected `Choice`.  
  
The `Submit Vote` button will be disabled until the user has voted on at least one `Choice`.

### ADMIN `EDIT POLL CONFIGURATION` PAGE

#### `Edit Poll Configuration` functionality includes the ability to:  
- edit the Poll `Title`
- edit the Poll `Subtitle`
- add a Poll `Choice`
- remove a Poll `Choice`
- edit a Poll `Choice Label`

##### `Choices`
The number of Poll `Choices` must be between 2 and 50. The system will enforce this limit by preventing the admin from removing a choice if there are only 2 choices remaining, and preventing the admin from adding a choice if there are already 50 choices.  
The system will also prevent choices with a duplicate title from being added or edited. The system will prevent Choices from being added with an empty string for the title. The system will provide feedback to the admin if one of these errors occurs.  

- **Adding a Poll `Choice`**  
	When adding a poll `Choice`, the system will add a new `Choice` to the end of the list of choices.
	The new `Choice` will have a default `Label` of "Choice #<number>" where number is the index of the new `Choice` (1 based).  
	The admin can edit the `Label` of the new `Choice` immediately after adding it, or at any time later.
	The system will enforce the limit on the number of Choices. The number of Choices can never be less than 2 or more than 50.  

- **Editing a Poll `Choice Label`**  
	When editing a poll, the system will allow the admin to change the `Choice Label`.  
	The system will also prevent `Choices` with a duplicate `Label` from being added.  
	The system will prevent `Choices` from being added with an empty string for the `Label`.  
	The system will provide feedback to the admin if one of these errors occurs.

- **Removing a Poll `Choice`**  
	When editing a poll, if an administrator removes a `Choice` for a poll that has not yet received any votes, then the `Choice` is simply removed from the `Poll Configuration`.  
	But a `Choice` can never be removed if it reduces the number of choices below 2.  
	When editing a poll, if an administrator attempts to remove a `Choice` for a poll after votes already exist for that `Choice`, then the existing votes for the removed `Choice` are also removed.  
	This will allow the users who made that `Choice` to vote again for one of the remaining `Choices`.  
	The system will enforce the limit on the number of `Choices`. The number of `Choices` can never be less than 2 or more than 50.  
	Note: a "(removed)" `Choice` and "(removed)" vote are not actually deleted but marked as `(removed)` in the database.
	When a `Choice` is marked as `(removed)`, the label of the `Choice` will have "(removed)" added as a suffix.  
	For the edge case where adding the suffix would cause the label to exceed 100 characters, the label will be truncated so that when appending the suffix "(removed)" the label will be 100 characters long.  

	After an administrator removes a `Choice`, the `(removed)` `Choice` disappears entirely from the `POLL-CARD` results and voting sides.  
	Since its votes are excluded from calculations, showing it as a 0% row would be misleading (it did not get 0 votes; its votes are hidden).  
	A clean removal is least confusing for voters. If the admin wants to see `(removed)` choices, that would belong in the admin view, not the public results page.    
	On a `FINAL-VOTE-POLL` (where participants normally cannot change their vote), if the administrator `(removed)` a `Choice`, the affected participant's votes are marked `(removed)`.  
	Re-vote is always allowed after choice removal — for this specific case, regardless of vote-mutability mode.  
	The case of a participant who has already voted for a `Choice` that is `(removed)` is handled by the system as follows:  
	- The participant's vote is marked as `(removed)` in the database.
	- The participant is enabled to vote again and will be presented with the revised poll to select a new `Choice`.
	- The participant's current vote state is `(removed)`, which is effectively "no current vote".
	- The participant will appear in the list of participants who have not yet voted, accurately reflecting their current state and alerting other viewers that they still need to vote.

	On a `PRIVATE_POLL_ANYONE_WITH_THE_LINK` poll, a participant's vote is `(removed)` (choice removal), and voting will enabled again, even if the poll is `FINAL-VOTE-MODE`.     
	A `(removed)` vote for a user means no active vote currently exists.
	The existing participant entry is reused when they submit their new vote. This is the cleanest UX and avoids incorrectly triggering flows.  

	`(removed)` `Choices` are excluded from exports, "same aggregate data a voter sees" principle. Including them would require the export to handle a "removed choices" section which is not needed. Admins who need historical detail could query the database directly if they need to. This is not in the scope of these requirements.         

	`(removed)` `Choices` are hidden from voters in the poll UI. When an administrator opens the "Edit Poll" view for that same poll they see `(removed)` `Choices`, labeled as "`(removed)`". The data is deliberately retained, and gives admins visibility into what was removed for the purposes of auditing ("which choices existed before?", "who lost their vote?"). 
	
	When editing a poll, there will be no functionality to UNDO a `(removed)` choice. However, the admin can add a new choice with the same label. The votes for the `(removed)` choice will not be restored. The re-added choice is simply treated as a new choice and will be displayed in the order it was added, not in the order it was originally created.

#### The `Edit Poll Configuration` page will also allow have a section to allow the admin to:
- change `POLL_STATE` using a dropdown box that has the items: `CLOSED-POLL-STATE` and `ARCHIVED-POLL-STATE`

	An ARCHIVED Poll is hidden from view by users, but its configuration and vote history are retained rather than removed.  
	When a poll is ARCHIVED, the END_DATE_TIME will be changed to the current date/time.  
	An ARCHIVED poll can be restored to `POLL_STATE`=`CLOSED-POLL-STATE` by the Admin.  
- set a `START_DATE_TIME` or set no `START_DATE_TIME` using a date/time picker  
- set an `END_DATE_TIME` or set no `END_DATE_TIME` using a date/time picker

- set ChoiceMode to one of `SINGLE-CHOICE-POLL` or `MULTIPLE-CHOICE-POLL`  
	- if a poll has received more than one vote for a choice, the `ChoiceMode` can not be changed to `SINGLE-CHOICE-POLL`
- set `ResultsVisibility` to one of `ANONYMOUS-POLL` or `TRANSPARENT-POLL`
- set `VoteMutability` to one of `FINAL-VOTE-POLL` or `DYNAMIC-VOTE-POLL`
- set `AccessMode` to one of `PUBLIC_POLL`, `PRIVATE_POLL_ANYONE_WITH_THE_LINK_POLL`, `PRIVATE_POLL_INVITATION_ONLY`
	- the `AccessMode` cannot be changed after the poll has received a vote

# Live Results Page
The `Live Results` page for a poll will just be a page that displays the title and subtitle of a poll.  
For a `TRANSPARENT-POLL`, the `Live Results` page is where the `userName`s of the voters will be listed.  
This feature will be implemented in a future version of the Poll WebApp.

# Other Requirements  
**SCALE**: Less than 10,000 concurrent voters per poll and 1000 active polls. As the site grows, techniques for scaling up will be required.

# EXCLUSIONS
The `Search` functionality is not required for this implementation.  

Render the filter bar for visual/layout fidelity to the reference design, as visible but non-functional, not wired to any Category field or filtering logic. That functionality will be implemented in a future version of the Poll WebApp.
  
For this implementation, no pagination or infinite scroll is required for the Home Page Grid, `Admin Poll List`, or the `Participants` list.  
  
The problem of detecting and preventing multiple votes from the same user is not required for this implementation.  
  
Archived/closed polls and their vote history are kept forever unless an admin action removes them some other way (none is currently specified).   

The full implementation of the `Live Results` page for a poll is not required for this implementation.

The `responsive-grid.html` file renders a "Create Poll" nav link in the main site header, but this is not part of the requirements for this implementation. The `Create Poll` link should be greyed-out. It will be specified later.

The `responsive-grid.html` file renders a "Search" box in the main site header, but this is not part of the requirements for this implementation. The search box should be greyed-out. It will be specified later.

Standard semantic HTML is used, but no formal accessibility (WCAG/screen-reader/keyboard-nav) compliance is targeted.

These features will come in a future implementation.
