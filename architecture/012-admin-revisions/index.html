01

Scope and shape of the change

012 is not one feature. It is a set of thirteen independent requirement groups that happen to land on the same three surfaces: the admin poll list (admin.html / adminList.js), the poll editing surface (admin-poll.html / adminPoll.js), and the public poll grid (index.html / pollGrid.js / pollCard.js). Grouping them is what makes the shared consequences visible: three of them independently require the same repair to the edit-lock check, and two of them independently push work from the client onto the server.

Two groups are defect reports rather than new behaviour (R5, R7), and both have the same root cause. Two are pure data-model changes (R3, R6). The rest are presentation and contract work. Every group is listed below with the blast radius that the code review behind this document established.

  • Logging, entirely. This revision withdraws it — no logging is added to any server-side endpoint by 012, and a dedicated requirements document will cover it. §9 keeps the volume analysis for that document to build on.
02

Component view

The layering does not change. What changes is where decisions are made: R11 moves the last of the row-enablement rules out of adminList.js, R1 removes a second write path out of adminPoll.js, and R6 moves the voter-limit ceiling out of the browser. In every case the browser gets simpler and service.ts gets one more rule.

03

Domain model

R3 is the only structural change to the Poll document, and it is a collapse rather than an addition. Today two independent enums describe a poll's audience and its transparency, and one of their six combinations is impossible. The server does not reject that combination — it silently rewrites the other field, which is why adminPoll.js has to re-fetch after every change to either select. Collapsing the pair removes the impossible cell, and with it the auto-correction, the re-fetch, and the class of bug where a user's explicit choice is overwritten without being told.

Naming convention

The five values carry spaces and hyphens, unlike the SCREAMING_SNAKE style of the enums they replace. That is deliberate and it has precedent: pollState already stores "WAITING TO OPEN" and "AWAITING APPROVAL" verbatim and renders them unchanged. Persisting the display string is what lets the requirement say "no code-to-label map is introduced" and have it be true at every layer — store, API, and radio label.

Invariants that must hold after 012

  1. Exactly one visibility field. No document carries accessMode or resultsVisibility; no code path reads them. Because the collections are dropped, this is checkable by grep rather than by query.
  2. pollVisibility is frozen once voteHistory has ever held a row for the poll. It inherits accessMode's existing rule; the freeze is what the update surface's static label reflects.
  3. voterCountLimit is null whenever pollVisibility is PUBLIC POLL. Switching to public clears any stored limit rather than preserving it for a later switch back, and switching the other way leaves the field blank — the old public→private auto-fill of 500 is deleted.
  4. A non-null voterCountLimit is an integer in 1…500, enforced in the browser and again in validatePollFields, where the server check is authoritative. A null limit on a private poll binds at 500, so no private poll admits a 501st voter by any path.
  5. The invited list is non-empty only for the two INVITATION ONLY values — but the list is retained, not cleared, when visibility moves away from invitation-only, so a switch back does not lose it.
  6. No poll is ever written with a state the schedule sweep would immediately contradict. §4 proves this for all three manual transitions.
04

Lifecycle and the three manual transitions

011 established eight stored states and a sweep that writes the schedule-appropriate state every ENV_POLL_DATE_CHECK_POLLING_INTERVAL. R10 adds three one-click buttons that write pollState directly. Those two mechanisms are in tension by construction: the sweep re-derives state from startAt and endAt and will happily undo an administrator's click within one tick. The requirements resolve this without an override flag, by making each manual transition write the schedule fields into a shape the sweep then agrees with.

Why the archive rule had to change

Today validateStateAction stamps endAt = now for both CLOSED and ARCHIVED. For archiving that is a data-integrity bug independent of 012: a poll that genuinely closed on the 1st and is archived on the 20th has its recorded close date rewritten to the 20th, and the JSON and Markdown exports carry the wrong date forever. R10 replaces the blanket rule with the three per-transition rules above, and archiving preserves endAt.

Transition guards

validateStateAction currently accepts only CLOSED and ARCHIVED. It gains OPEN and a from-state guard per target, and the same predicate produces the row capabilities in §7 — one rule, two consumers, no drift.

Consequence worth stating in the spec

Reopening a poll whose endAt was in the past leaves it with no end date at all — it becomes an open-ended poll until an administrator sets a new end through the update surface. This follows directly from the stated rule and is almost certainly intended (an end date in the past cannot coexist with "open"), but it is a real, user-visible consequence that the spec should say out loud rather than leave to be discovered.

05

Runtime views

5.1 — One write path on the editing surface (R1, R2)

The editing page has two save paths today: PUT …/choices behind its own Save Choices button, and POST …/publish behind Save and Publish. Because only the second is wired to the page's dirty flag, editing only the choices leaves Save and Publish disabled — the reason R1 explicitly calls out "editing only the choices must enable Save and Publish". Folding the paths together fixes that as a side effect of removing the route.

Two details the spec must pin down

Choice immutability still applies. PUT …/choices refuses when the poll has ever been voted on. After the fold, that check moves into the publish handler's UPDATE branch: the allowed-field whitelist grows a rejection for labels, alongside the existing rejection for everything outside title / subtitle / startAt / endAt.

Cancel must still release the lock. R2 enables Cancel before any edit is made. Because the page holds an editing session from the moment it loads, an always-enabled Cancel is now the most likely way a session ends — it must run the same DELETE …/edit-session teardown as the back button, or every cancelled edit will leave a poll stuck in EDITING until the stale-lock sweep reclaims it one heartbeat interval later.

5.2 — Participant moderation under an active edit lock (R5, R7)

R5 and R7 are reported as two bugs. They are one bug, in refuseWhenNotConfigurable, reached by three endpoints. The editing page acquires an edit-session lock on load, which sets pollState = "EDITING"; the three participant endpoints then refuse every request from that same page with "This poll is currently being edited. Please try again shortly." The invite row surfaces the refusal, which is R5's visible error. The ban button writes the refusal into #inviteError — an element hidden whenever the poll is not invitation-only — which is R7's silent failure.

Design point: which modes may moderate

resolveEditContext returns EDIT or UPDATE. Participant moderation must be accepted in both — banning a voter from a poll that already has votes is the main reason the feature exists. Only the invite row is narrowed further, and by visibility rather than by mode: it renders for the two INVITATION ONLY values and is absent otherwise. The ban and un-ban actions stay available for all five values, including PUBLIC POLL. Refusals for AWAITING APPROVAL and ARCHIVED survive unchanged, because editModeFor still produces them.

R7 also needs a presentation fix that has nothing to do with the lock: the ban button must write its error into an element that is visible in every visibility mode, not into the invite row's #inviteError.

5.3 — Voting while a poll is EDITING (R8)

An administrator opening the editing page moves a live poll to EDITING instantly, while voters have the grid open. R8 enumerates four windows, each needing its own reaction, and closes them with a single summary rule: any time there is a user action on the poll card, or the card is refreshed, a poll in EDITING renders its front face carrying the "Try Again" message. Every window therefore ends on the front face — the message is the same string in all four — and the only thing that varies is what triggers the flip. The second invariant is quieter but just as binding: a voter never loses a selection they had made.

The one message

R8 defines exactly one string, used on the card face and on every refusal:
"This poll is momentarily unavailable to cast a vote. Please try again shortly."

The listing rule R8 depends on — now specified

None of this works if the card is not on the grid to begin with, and 011 FR-003 withholds EDITING from the public listing entirely: GET /api/polls filters on pollState ∈ {WAITING TO OPEN, OPEN, CLOSED} and GET /api/polls/:pid 404s anything outside it. The requirements now close this directly — both endpoints admit EDITING only when pollStateBeforeEditUpdate is itself one of the three public states. A poll that was public before the edit stays visible and shows the message; a poll that was never public (INITIALIZED, REJECTED) stays hidden, so 011's intent survives intact.

Implementation note: this makes pollStateBeforeEditUpdate — until now purely an internal restore field — part of a public read path. It must never be emitted in the response; it is a filter input only.

5.4 — The home grid becomes a polling list (R13)

Today the grid fetches GET /api/polls exactly once, at load, and each mounted card then polls GET /api/polls/:pid on its own timer. A poll created, opened or closed after page load never appears or disappears until a manual reload — which is what R13 fixes. Doing it naively adds a request per interval on top of the N the cards already make; the list response already carries the full card payload, so the same change can remove the fan-out instead of adding to it.

Do not lose these two card behaviours

pollCard.js already preserves an in-progress selection across a refresh only while the card is flipped. R8's W1 forces a flip back to the front while the poll is being edited, and R8's assumption section states the selection must survive that and be restored at W5. The preservation rule therefore has to be decoupled from the flip state — an explicit "pending selection" held per card, independent of which face is showing.

Server-computed row capabilities

011 already sends five booleans per admin row so the client renders the action menu without re-deriving any state rule. R10 adds five one-click controls and four icons, every one of which has an enablement condition — so R11 extends the same principle rather than letting adminList.js start reasoning about pollState again. Extract the whole set into one capabilitiesFor(poll, hasEverBeenVotedOn) in service.ts, called by the list endpoint and asserted directly by tests.

Duplicate, Copy Link and View Results have no state condition and are always enabled; the requirements give an enablement rule only for Delete.

08

Presentation architecture

8.1 — Anatomy of an admin row

The list goes from nine columns to ten, and from one line per poll to up to three. Subtitle and the two screening columns leave the header row and become stacked lines inside column 1, which is what makes the row variable-height — and why the requirement specifies that zebra striping alternates per poll, not per rendered line.

Empty-date rendering

Columns 7 and 8 render lower-case sentinels rather than the current em-dash: an empty startAt reads started, an empty endAt reads does not end. Both are statements about the poll rather than about the absence of data, which is what makes them worth the change — and both become considerably more common after R10, since the OPEN transition clears startAt unconditionally.

The kebab menu keeps its job

Promoting seven actions to one-click controls does not remove the menu. It keeps every action in words, which is the only place an administrator can read what an icon does without hovering it. Icons and menu items dispatch the same handlers; the menu is a second affordance for the same capability set, never a second rule set.

8.2 — Radio groups on the editing surfaces

Three selects become three single-select radio groups (R4). The mechanical consequence is small — the same draft field, the same dirty flag, the same publish payload — but there is one behavioural consequence worth naming: with a select, a change costs two clicks and is easy to abandon; with radios, a stray click is one click from changing a poll's visibility. The always-enabled Cancel of R2 is what makes that recoverable, which is a good reason to treat R2 and R4 as one story rather than two. The exposure is bounded to the edit surface only — once a poll has a vote, all three groups become static labels.

Edit surface — no votes yet

All three render as radio groups. Voter Count Limit is enabled unless pollVisibility is PUBLIC POLL, in which case it is disabled, greyed and cleared to null. The invite row renders for the two INVITATION ONLY values.

Update surface — poll has votes

All three render as static labels: the requirements now freeze choiceMode and voteMutability alongside pollVisibility once a poll has been voted on. That aligns the surface exactly with the publish endpoint, which already accepts only title, subtitle, startAt and endAt in this mode — so no field on the page is rendered as editable when the server would refuse to write it.

8.3 — The Poll Administration menu item (R9)

The requirement is precise and the architecture adds nothing to it: one shared predicate, one boolean on GET /api/me, one conditional menu item between Edit Profile and Logout, and no change whatsoever to the server-side gate. The one thing worth restating in the spec is the security posture the requirement already states — isAdmin is a rendering hint. Forging it in devtools reveals a menu entry whose target, GET /admin behind requireAdmin, still returns 403.

// service.ts — one predicate, two callers
export function isAdminEmail(email: string | undefined, config: AppConfig): boolean {
  if (!email) return false;
  return config.admins.includes(email.trim().toLowerCase());
}

// createRequireAdmin  → the authorization decision   (unchanged behaviour)
// GET /api/me         → the isAdmin rendering hint   (new)

config.admins is already trimmed and lower-cased at load, so the predicate's only job is to normalise the incoming address the same way — which is exactly what createRequireAdmin does inline today. Extracting it is a refactor with no behaviour change, and it is what makes "the two can never drift" true rather than aspirational.

09

Observability

R12 withdrawn in this revision

The requirements now state that no logging is to be added to the server-side endpoints by 012, and that a dedicated requirements document will cover logging in full. The previous revision of this architecture specified a log line for the two poll-list queries; that is removed from scope, and nothing in 012 changes the current logging behaviour.

The section is kept rather than deleted because the analysis behind it survives the withdrawal, and the logging document that follows will need it. The two poll-list endpoints are the worst possible place to start logging naively, and it is worth knowing why before that document is written.

Why the two list endpoints need a volume rule

Neither endpoint is requested on demand. The home grid re-fetches GET /api/polls every ENV_POLLING_INTERVAL (5 s) per open tab once R13 lands, and the admin list re-fetches GET /api/admin/polls every ENV_POLL_ADMIN_PAGE_REFRESH_INTERVAL (5 s) per open tab today. A log line per matched poll therefore costs, for a modest 20-poll deployment with three tabs open:

20 polls × 12 fetches/min × 3 tabs = 720 log lines per minute, indefinitely, on an idle system.

On DigitalOcean App Platform that fills the log retention window with unchanging rows within hours, and buries anything diagnostic. Three shapes bound it, in increasing order of machinery:

  1. One summary line per request carrying every matched triple — same information, 36 lines per minute instead of 720, still greppable.
  2. Log only on change — emit when the match set differs from the previous request. Near-zero on an idle system, but needs per-process state.
  3. Sample or level-gate — a debug level that is off in production. Standard, and the natural fit once a real logging library is introduced.

Whichever the logging document picks, the rule it must state is that polled endpoints do not get per-item logging at info level. That is the finding worth carrying forward.

10

Architecture decisions

AD-01

Persist the five visibility values as display strings

Decision
pollVisibility stores "PUBLIC POLL" and the four "PRIVATE POLL - …" strings verbatim; no code-to-label map exists at any layer.
Why
The requirement states it directly, and pollState sets the precedent — it already stores and renders "WAITING TO OPEN" unchanged. A map would reintroduce the drift the collapse is meant to remove.
Cost
The strings are long and appear in query filters and test fixtures. Export them as a POLL_VISIBILITIES const array beside POLL_STATES so no literal is ever retyped.
AD-02

No override flag for manual state transitions

Decision
The three buttons write startAt and endAt such that evaluateSchedule re-derives the state just chosen. No manualOverride field is added and the sweep is not modified.
Why
An override flag needs a lifecycle of its own — when is it cleared, does editing the schedule clear it, does archiving? The schedule-field rules need none of that, and they leave the poll's dates telling the truth about the poll.
Cost
Reopening a poll discards a past end date (§4). This must be stated in the spec as intended behaviour, not left to be found.
AD-03

Extend resolveEditContext rather than relax refuseWhenNotConfigurable

Decision
All three participant endpoints adopt the lock-aware check and accept a clientGuid; refuseWhenNotConfigurable is deleted.
Why
Simply dropping the EDITING refusal would let a stale tab moderate a poll another administrator now holds. resolveEditContext already draws exactly the right line — the lock holder proceeds, everyone else is refused — and reusing it means one rule, not two.
Cost
Two DELETE routes must carry clientGuid. Pick body or query for all three consistently (see §6).
AD-04

The server is the only arbiter of a vote during EDITING

Decision
validateVoteSubmission gains an explicit EDITING branch returning 409 with the retry message; the card's front-face suppression is a courtesy, not a guarantee.
Why
W4 — the state changing between click and handler — is unreachable by any client-side check, and a voter following a direct ?PID= link may never have seen the grid at all.
Cost
A distinguishable error message, which the card must map to "return to the back face and retry" rather than the closed-poll treatment.
AD-05

Feed the grid's cards from the list response

Decision
GET /api/polls resolves the caller's session and returns full PollDetail objects including myChoiceIds; cards render from the list payload instead of each polling its own endpoint.
Why
R13 as written would add one request per interval on top of N. The list endpoint already builds the identical payload, so the same work collapses N + 1 into 1 and removes a class of inconsistency where a card and the grid disagree about the same poll.
Cost
A public endpoint now reads the session. It already does so on the single-poll route, and the response for a guest is unchanged.
AD-06

One capability function, two consumers

Decision
capabilitiesFor(poll, hasEverBeenVotedOn) in service.ts produces all seven booleans; the list endpoint spreads it, and validateStateAction enforces the same from-state guards.
Why
R11's stated goal is that the client re-derives no state rules. A shared function makes the button's enablement and the endpoint's refusal provably the same predicate, and gives the tests one place to assert.
Cost
None material — this is the existing inline block in GET /api/admin/polls, extracted and extended.
AD-07

Drop both collections; no migration path is written

Decision
polls and voteHistory are deleted at deploy, per the requirements' opening paragraph. No dual-read, no back-fill, no tolerance for documents carrying the old fields.
Why
The requirement grants it explicitly, and the alternative costs a mapping layer for a field that exists only to be read.
Cost
Irreversible for any data in the target environment. The spec's quickstart should say so in the deploy step, in as many words.

Inconsistencies, ambiguities and unspecified aspects

How these are classified

Inconsistencies are places where the requirements document contradicts itself. Conflicts between the requirements and the system as currently built are a different thing — they are the work the feature exists to do — and are listed separately below as deltas, which do not count against the success criteria.

Inconsistencies within the requirements document

#FindingResolution taken here
I1The pen icon's disabled case is stated as exhaustive. "If editPoll and updatePoll are not available, the pen icon will be disabled. This is the case for a poll that is pollState=ARCHIVED." But the same document describes polls in AWAITING APPROVAL (a screening is running) and EDITING (another tab holds the lock), neither of which can open an editing surface either.Read "this is the case for" as illustrative, not exhaustive. The pen follows canEdit || canUpdate, which is already false for all three states — so the capability booleans give the correct behaviour without a special case.
I2"Only the front-side" is asserted absolutely, then contradicted. I3The new enum is defined in terms of a token it removes. Ambiguities resolved by default

  • What a blank voterCountLimit is stored as on a private poll. The document says the field "will not be auto-filled with 500" and also that "if the field is left blank, then the limit will be 500" — so the stored value and the effective value differ. Read as: persist null, resolve to 500 at vote time (A7).
  • The scope of "the same function as the back icon." The requirements now pin which control Cancel mimics — the header's back icon, explicitly not the browser's — but not whether the unsaved-changes prompt survives, nor that the editing session is released. Read as: same destination, same session teardown, prompt retained when dirty (A2, A3).
  • Whether the PUBLIC POLL parenthetical is part of the stored value. The unclosed backtick and parenthesis leave the literal's boundary unclear. Read as prose; the stored string is PUBLIC POLL (I3).
  • Whether the two SHOW WHO VOTED variants differ at all yet. The document states the flag "is not currently used" while listing it as a distinguishing part of four values. Read as: persisted and rendered, behaviourally inert — including in the admin results page, whose notYetVoted list stays gated on invitation-only.
  • Zebra striping colours. Unspecified. Taken from the existing admin.css surface tokens rather than introducing new ones.

Unspecified aspects worth a line in the spec

  • The kebab menu's column number is never stated. Columns 1–9 are numbered explicitly; the kebab is described only as "at the far right". Implied 10th.
  • "All three participant endpoints" are never enumerated. The instruction to adopt resolveEditContext also sits under the state-transition heading rather than with the Add Participant and Ban defects it belongs to. Taken as POST …/invited, DELETE …/participants/:email and DELETE …/banned/:email.
  • The shape of the value the vote endpoint returns during EDITING. The requirements say the handler "will return a value that instructs the client-side to render the poll card front-side" but not what that value is. Default: a 409 with a distinct error code alongside the message, so the client never string-matches (A8).
  • Whether the updatePoll page renders the choices box at all. R1 folds choice saving into Save and Publish "on the editPoll page"; choices are immutable once voted on. Default: render them read-only, and reject labels in the publish handler's UPDATE branch.
  • What <elapsed> on the screening line measures from. No field records when a poll entered AWAITING APPROVAL. Default: the existing waitingFor behaviour — measured from pollApprovalTimestamp, showing queued before a screening attempt is claimed (A9).
  • The default pollVisibility for a newly created poll. Not stated. Default: PUBLIC POLL, matching today's default pair (A1).

Recommended sequencing

The thirteen groups are not equally coupled. Ordering them by what the next slice depends on gives four natural stories:

  1. R3 + R6 — the model collapse. Touches the most files and every test fixture, and every other group reads the new field. Doing it first means nothing is written twice.
  2. R5 + R7 + R1 + R2 — the editing surface. One root cause, one write path, one dirty flag, one Cancel. Small, self-contained, and it closes both live defects.
  3. R10 + R11 + R4 — the admin surfaces. The capability function comes first, the row layout renders from it, and the radio groups land alongside.
  4. R13 + R8 + R9 — the public surface. R13's polling loop is the vehicle R8's four windows ride on, so they belong together; R9 is independent and can land anywhere. R12 is withdrawn and contributes no work.
