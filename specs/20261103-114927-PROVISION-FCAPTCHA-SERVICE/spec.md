## User Scenarios & Testing *(mandatory)*

The actor in every story is the **operator**: the developer who runs CrowdPoll's hosting on DigitalOcean.
Visitors are affected only by the outcome: a site that, once provisioned, shows the human check before sign-in.

### User Story 1 - The operator provisions the whole CrowdPoll stack from one reviewed command (Priority: P1)

The operator has filled in the local secrets file.
They run one command that shows, before anything happens, every resource it will create: the app with its `web` and `fcaptcha` services, the routing that sends `/fcaptcha` to the human-check service and everything else to `web`, the `crowdpoll.vote` domain, the PostgreSQL and Valkey databases with their access rules, and the Spaces bucket with its CDN.
They confirm, and the stack is built with the same names as today and the human check turned on.
Running the same command again changes nothing.

**Why this priority**: It is the feature's purpose: CrowdPoll's hosting, the new FCaptcha service included, described once and provisioned without clicking around the console.

**Independent Test**: On an account where the old stack has been deleted, run the preview, confirm the list, apply, and check that `https://crowdpoll.vote/fcaptcha/health` answers, `https://crowdpoll.vote/healthz` answers and the sign-in page opens with the human check; run the command again and see "no changes".

**Acceptance Scenarios**:

1. **Given** a complete secrets file and no CrowdPoll resources on the account, **When** the operator runs the preview, **Then** it lists every resource to be created, with secret values hidden, and changes nothing.
2. **Given** the preview has been shown, **When** the operator confirms, **Then** every listed resource is created with the names of FR-002, and both services reach a healthy state.
3. **Given** the stack has been applied, **When** the operator runs the preview again without changing the configuration, **Then** it reports no changes.
4. **Given** the stack is running, **When** a guest opens `https://crowdpoll.vote/login`, **Then** the human check is shown first, served from the site's own domain, and passing it shows the sign-in form.
5. **Given** the stack is running, **When** the operator changes one setting in the configuration and previews, **Then** the preview shows only that change.

### User Story 2 - The operator prepares the secrets and retires the old stack safely (Priority: P1)

Before anything is deleted, the operator fills a local, never-committed secrets file from a committed example that names every value.
The command refuses to go further while any value is empty.
Only then is the old stack deleted, once, in the console: the app, the two databases and the emptied Spaces bucket.
The test users' data is not carried over.

**Why this priority**: The old app's secrets are held by the hosting platform in a form that cannot be read back; deleting the old stack before they are replaced would leave the new one unable to send mail or store files.

**Independent Test**: Leave one value of the secrets file empty and run the preview: it refuses and names the value; fill it and the preview runs.

**Acceptance Scenarios**:

1. **Given** a secrets file with any required value empty, **When** the operator runs the preview, **Then** it stops before showing a plan and names each empty value.
2. **Given** the repository after this feature, **When** every committed file is searched, **Then** no secret value is found, and the secrets file, the state and the tool's working folder are listed as ignored.
3. **Given** a complete secrets file, **When** the operator follows the documented switch-over, **Then** the order is: secrets complete → old stack deleted → apply → after-apply checks.
4. **Given** the signing and verify secrets of the human check, **When** the stack is applied, **Then** they are generated by the provisioning itself, are at least 32 random bytes, differ from each other, and `web` and `fcaptcha` hold the same verify secret.

---

### User Story 3 - The operator releases a new version of the code without the console (Priority: P2)

Automatic deploys stay off.
When the operator wants `main` in production, they run one committed command that starts a deployment of the app and reports whether it succeeded.

**Why this priority**: Without it, every release after this feature would still need the console, against the requirement; it is needed only once the stack exists.

**Independent Test**: With the stack running, merge a visible change to `main`, run the deploy command, and see the change live and the command report success.

**Acceptance Scenarios**:

1. **Given** the stack is running and `main` has a new commit, **When** the operator runs the deploy command, **Then** a deployment of `main`'s current commit starts and the command reports its final state.
2. **Given** a deployment fails, **When** the command finishes, **Then** it reports the failure and the phase it failed in, and the previous version keeps serving.
3. **Given** a push to `main`, **When** nobody runs the deploy command, **Then** production does not change.

---

### User Story 4 - The documentation describes the new way (Priority: P3)

The old hand-kept app description is removed, and the project's README, architecture document and agent instructions explain the infrastructure folder, the secrets file, the state file and its backup, the switch-over and the deploy command.

**Why this priority**: It keeps a second, drifting description of the app from coming back; it follows the working stack.

**Independent Test**: Search the repository for the old app description file and for the "change it in both places" rule: neither remains; the README's deployment section names the infrastructure folder.

**Acceptance Scenarios**:

1. **Given** the feature is complete, **When** the repository is searched, **Then** `.do/app.yaml` does not exist and no document refers to it as current.
2. **Given** a new operator reads the README's deployment section, **When** they follow it, **Then** they can fill the secrets file, preview, apply, check and deploy without other documents.

### Edge Cases

- **The tool cannot run on the operator's machine** (the machine's application control policy already blocks the DigitalOcean CLI): the first step checks that the provisioning tool starts; if it is blocked, the open-source equivalent is tried, then the machine's policy setting is reviewed.
- **An apply fails part-way**: some resources exist and others not; running the apply again finishes the rest without duplicating what exists. Until it succeeds, nothing is serving, which is accepted while there are only test users.
- **The deleted bucket name cannot be reused at once**: the apply waits and is retried, or the bucket takes a new name and the CDN address in the settings follows it.
- **The domain's certificate is still being issued** after the apply: the after-apply checks against `crowdpoll.vote` wait for it; the app's default address can be checked meanwhile.
- **The provisioning tool does not accept Valkey as an app database attachment**: this is reported as a gap of the tool, not worked around by hand.
- **The human-check service cannot reach database 1 of Valkey** (the appended `/1` is not resolved): the service's health check fails; `web` fails open by design, counts the skipped checks, and the after-apply check reports it.
- **The state file is lost**: the resources still exist but the tool no longer knows them; the documented backup restores it, and without one the resources are adopted again by import.
- **The access token expires during an apply**: the apply stops with an authorisation error and is run again with a new token.
- **The secrets file holds a value that the service rejects** (for example an SES key that does not work): the after-apply sign-in email check fails and names the setting, and the operator fixes the file and applies again.

## Requirements *(mandatory)*

### Functional Requirements

**What is provisioned**

- **FR-001**: One committed configuration, in a top-level `infra/` folder, MUST describe every DigitalOcean resource of CrowdPoll:
  the app (`web`, `fcaptcha`, the routing rules and the `crowdpoll.vote` domain), the PostgreSQL cluster, the Valkey cluster, their access rules (only the app may connect), the Spaces bucket and its CDN.
  The DNS zone, Amazon SES and OpenSearch MUST NOT be part of it.
- **FR-001a**: The app's `crowdpoll.vote` domain entry MUST name its DigitalOcean DNS zone, so that the apply itself points the domain at the new app, with no manual DNS step.
- **FR-002**: The resources MUST keep today's names and region: `tor1`, `db-pgsql-tor1-crowdpoll`, `valkey-tor1-crowdpoll`, the bucket `crowdpoll` and its CDN address `https://crowdpoll.tor1.cdn.digitaloceanspaces.com`, the app `crowdpoll` and the domain `crowdpoll.vote`.
  The one exception: when DigitalOcean has not yet released the bucket name `crowdpoll` at the switch-over, the bucket MAY take a new name, and `ENV_SPACES_BUCKET` and `ENV_SPACES_CDN_URL` MUST follow it.
- **FR-003**: The routing MUST send every path under `/fcaptcha` to `fcaptcha` with the prefix removed, and every other path to `web`.
- **FR-004**: `web` MUST carry its current settings and, in addition, the human check turned on: `ENV_FCAPTCHA_ENABLED=1`, `ENV_FCAPTCHA_URL` set to `fcaptcha`'s private address, `ENV_FCAPTCHA_SITE_KEY` and the shared verify secret.
  `ENV_OPENSEARCH_URL` MUST stay unset.
- **FR-005**: `fcaptcha` MUST be built from `fcaptcha-server/` on `main`, health-checked at `/health`, scaled between 1 and 3 instances, with its site keys including `web`'s site key, its allowed hostnames naming every domain of the app, and its store in Valkey database 1.
  The allowed hostnames MUST be derived from the app's domains, so that none can be missing.
- **FR-006**: Database addresses and certificates MUST be given to the services by reference to the databases, never as copied values.
- **FR-007**: Automatic deploys on push MUST stay off for both services.

**How it is provisioned**

- **FR-008**: The operator MUST be able to see, before any change, a preview listing every resource to be created, changed or deleted, with secret values hidden; nothing MUST change without the operator's confirmation.
- **FR-009**: Applying an unchanged configuration MUST change nothing;
  a preview of it MAY show only a documented provider gap limited to SECRET env values, and any other difference fails.
- **FR-010**: The provisioning tool's DigitalOcean plugin MUST be pinned to one exact version, recorded in a committed lock file.
- **FR-011**: The first documented step MUST check that the provisioning tool runs on the operator's machine.
- **FR-012**: A change to the hosting after this feature (a setting, a size, a service) MUST be made in the configuration and applied, never in the console.

**Secrets and credentials**

- **FR-013**: No secret value MUST appear in any committed file.
  Values that exist outside the provisioning (`ENV_BETTER_AUTH_SECRET`, the SES keys, the Spaces keys, `ENV_ALLOWED_EMAILS`, any `ENV_OAUTH_*`) MUST come from a git-ignored local secrets file;
  a committed example file MUST name every one of them with an empty value.
- **FR-014**: The preview MUST refuse to run while any required value of the secrets file is empty, naming each one.
- **FR-015**: The human check's signing secret and verify secret MUST be generated by the provisioning itself: at least 32 random bytes each, different from each other, the verify secret identical on `web` and `fcaptcha`.
- **FR-016**: The provisioning's record of the resources (its state) MUST be kept locally and git-ignored; because it holds every secret in plain text, the documentation MUST tell the operator to back it up in encrypted form (for example as a password-manager attachment), and to keep both the state and the secrets file out of cloud-synced folders.
- **FR-017**: The provisioning MUST use a DigitalOcean access token limited to the resources it manages, with a short expiry, given in the session and never written to a file, and a Spaces key pair for the bucket.
- **FR-018**: No command of this feature MUST print a secret value, a token or a full email address.

**Switching over**

- **FR-019**: The switch-over MUST follow this order: the secrets file complete (FR-014) → the old stack deleted once in the console (the app, the PostgreSQL and Valkey clusters, and the Spaces bucket after it is emptied) → the apply → the after-apply checks.
  This deletion MUST be the feature's only console step.
- **FR-020**: The test users' accounts, polls, votes, invitations and sessions MUST NOT be carried over; the new databases start empty and the app creates its schema on start-up as today.
- **FR-021**: Before the old SES access key and the old Spaces keys are revoked, the new stack MUST have sent a sign-in email and served an asset from the CDN.

**Checking and deploying**

- **FR-022**: After an apply, the documented checks MUST confirm that `https://crowdpoll.vote/fcaptcha/health` answers, `/fcaptcha/fcaptcha.js` loads, `web`'s `/healthz` answers, the sign-in page shows the human check and one check can be passed, and (once, by hand, with a database client) that the human-check service's keys are in Valkey database 1.
- **FR-023**: A committed deploy command MUST start a deployment of the app at `main`'s current commit through the DigitalOcean API, with the same token, and report the deployment's final state and, on failure, the failing phase.
- **FR-024**: If the provisioning tool refuses Valkey as an app database attachment, the run MUST stop and report it as a gap of the tool.

**Documentation**

- **FR-025**: `.do/app.yaml` MUST be deleted, and the README's deployment section, `ARCHITECTURE.md` and `CLAUDE.md` MUST describe `infra/`, the secrets file and its example, the state file and its backup, the switch-over and the deploy command.
- **FR-026**: `.gitignore` MUST list the tool's working folder, the state files and the secrets file of `infra/`.

### Key Entities

- **Infrastructure configuration**: the committed description of every resource of FR-001, its settings and their non-secret values; the only description of the app.
- **Secrets file**: the git-ignored local file of the values of FR-013; its committed example names each value.
- **State**: the provisioning tool's local, git-ignored record linking the configuration to the real resources; holds every secret in plain text.
- **Old stack**: today's app, databases and bucket, created by hand; deleted once at the switch-over.
- **New stack**: the same resources, with the same names, created by the provisioning, with `fcaptcha` and the human check added.
- **Deployment**: one rollout of the app at a commit of `main`, started by the deploy command.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From a complete secrets file, the operator brings up the whole stack with one preview and one confirmation, and the site answers at `crowdpoll.vote` within 45 minutes.
- **SC-002**: A second preview right after the apply reports zero changes, apart from a documented provider gap limited to SECRET env values.
- **SC-003**: A search of every committed file after the feature finds zero secret values.
- **SC-004**: After the switch-over, a test user can open the sign-in page, pass the human check and receive a sign-in email on the first attempt.
- **SC-005**: A new version of the code reaches production with one command and no console visit.
- **SC-006**: The whole feature, from secrets to a released version, needs exactly one console visit: the deletion of the old stack.

## Assumptions

- CrowdPoll has only test users, so the downtime of the switch-over and the loss of the test data are accepted.
- The provisioning tool is Terraform (or its open-source equivalent, OpenTofu, if Terraform cannot run on the operator's machine), with DigitalOcean's own plugin; this choice is the stakeholder's, made in the requirements.
- The DigitalOcean CLI is not used.
- The operator runs everything from their own machine; there is no CI pipeline for provisioning.
- `main` on GitHub already holds `fcaptcha-server/` and the web app's FCaptcha support.
- The SES sending identity (`mail.crowdpoll.vote`), its DNS records and the IAM user stay as they are; only a new access key is issued.
- The current non-secret settings of `web` in `.do/app.yaml` are the values to carry over; where the README and the file disagree (the README's 4–12 instances, the file's 1–1), the file's values are taken.
- That a failed deployment leaves the previous version serving (US3, scenario 2) is App Platform behaviour; this feature does not test it.
- The `crowdpoll.vote` DNS zone is hosted at DigitalOcean; its other records (the SES ones among them) stay as they are and are not managed by the provisioning.
