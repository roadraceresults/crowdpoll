## Notes

Validated on 2026-08-28 against `designDocs/011-high-level-requirements-SIMPLIFY-POLL-STATES.md`
(469 lines). All 16 items pass on the first iteration. The specification contains 10 prioritized
user stories, 9 edge cases, 59 functional requirements, 14 success criteria and 10 assumptions.

**Why there are no [NEEDS CLARIFICATION] markers.** The source document was reviewed across
nineteen revisions against a state-machine model covering 8 states x 10 events. Every cell in that
grid has a defined outcome, all seven poll fields have a clearing path for every path that sets
them, and every route out of the awaiting-approval state terminates. Twelve mechanical checks and
four structural checks return zero on the source document. The questions that would otherwise have
been raised here were resolved in the source document itself.

**Implementation-detail scan.** The specification was searched for technology names, stored-field
names, endpoint names and background-process names. The only surviving reference is the assumption
that names those categories in order to state that they are deliberately deferred to
`/speckit-plan`. No identifier from the source document (`pollStateBeforeEditUpdate`,
`pollApprovalTimestamp`, `staleEditUpdateSweep`, `pollsAwaitingApprovalSweep`, `pollDateCheckSweep`,
`saveAndPublishPoll`, `startEditUpdate`, or the page names) appears in the specification.

**Naming decisions.** The eight poll states are treated as domain vocabulary rather than
implementation detail: the source document requires them to be displayed to administrators exactly
as stored, so the specification names them directly, in lower case prose form. The schedule fields
are described as "start time" and "end time" rather than by their stored names, which the source
document settled as keeping their existing form.

**Configurable timings** appear as named intervals rather than literal values, except in SC-005,
SC-007 and SC-010 where a concrete figure is needed to make the criterion measurable. The full set
of defaults is recorded in the Assumptions section.

**Scope carried deliberately.** User Story 10 covers the environment-variable rename for features
001 and 002. It changes no behaviour and would not otherwise warrant a user story, but the source
document assigns it to this feature, and this feature introduces six new settings that would
otherwise entrench the inconsistency.
