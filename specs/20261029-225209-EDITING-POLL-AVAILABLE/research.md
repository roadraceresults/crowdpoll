# Research: Editing an Open Poll Without Interrupting Voting

All file:line references were verified against the working tree at the time of planning (branch `editing-poll-available`, after the merge of `main` that brought `013-line-graph-enabled`).

## R1. Voting during editing: publish the stashed state in the projection

**Decision**: While a poll is `EDITING`, `projectPoll` publishes the *effective* state — `pollStateBeforeEditUpdate ?? "INITIALIZED"` — instead of the raw `EDITING`. Nothing else in the vote path changes.

**Rationale**: The vote path never reads the poll row for state: `castVote` validates against the cached projection (`src/votes/votePath.ts:146-160`, reading `poll:<pid>` via `src/polls/versions.ts:73-84`), and the voter card decides to hide its vote controls from the same projection field (`pollCard.js:1103-1105` via `deltaClient.js:115`). Taking the edit session today republishes the projection with `pollState: "EDITING"` (the state change bumps `content_version`, `src/polls/store.ts:699-700`), which is exactly what makes voters see "momentarily unavailable" and makes `validateVoteChoicesAndState` refuse with `409 POLL_EDITING` (`src/polls/service.ts:457-463`). Publishing the stashed state instead makes an open poll look OPEN to every voter-facing reader at once: the vote path, the poll card, deltas and listings (which already treat EDITING-stashed-OPEN as listed via `home_listable`, migration `002-polls.ts:28-31`, and `src/trending/recompute.ts:79-89`). The edit session itself is untouched: exclusivity, heartbeat, the stale sweep (`src/polls/sweeps.ts:147-170`) and the admin views (which read the raw row through `adminListRow`, `src/routes/pollsApi.ts:693`) all keep working on the real `pollState`.

The `EDITING` branch of `validateVoteChoicesAndState` and the poll card's `updateEditingState` (`pollCard.js:1139-1155`) become unreachable through the projection but are left in place (Principle III): they still guard the direct-service path and any stale cached projection.

**Alternatives considered**: (a) adding `pollStateBeforeEditUpdate` to the projection and teaching the vote path and the card to interpret it — two consumers change instead of one producer; (b) no longer moving the poll to `EDITING` at all — breaks the session's atomic claim (`pollsApi.ts:269-279`), the stale sweep's query (`store.ts:797-807`) and `/colors`' restore, far more invasive.

## R2. The pending change set (NC1)

**Decision**: One new nullable `polls` column, `pending_update jsonb`, plus `pending_rejection_reason text`, added by migration `014-pending-update`. On a save (`POST /publish`) of an **ever-voted poll whose effective state is not INITIALIZED**, the route splits the request: fields that carry no screenable text — `startAt`, `endAt`, `choiceMode`, `voteMutability`, `pollSharingMode`, `colors`, `lineGraphEnabled`, `invitedVoterList`, `bannedVoterList`, `voterCountLimit` — are validated and applied immediately in the save transaction, with **no state change** (the poll stays OPEN; no `AWAITING APPROVAL`). Changes to `title`, `subtitle` or the choice list are validated immediately (R3) but stored in `pending_update` as `{ title?, subtitle?, choices? }`, where `choices` is the complete new list with ids already minted for additions. The approval sweep screens and applies them.

**Rationale**: Today the same route sets `AWAITING APPROVAL` unconditionally (`pollsApi.ts:571-578`), which unlists the poll (`home_listable`) and refuses votes until the sweep approves it — the exact unavailability NC1's accepted resolution removes. Holding only the screenable content (what `screenWithTimeout` actually reads: title, subtitle, choice labels — `sweeps.ts:207-216`, `screening.ts:29-46`) keeps the poll serving its pre-save content, while everything the screener never looks at takes effect at Save per UA7. The choice list travels as one pending unit even when a save only deletes choices: additions and deletions from one merge then apply atomically (a rename = delete + add never half-applies), and there is exactly one apply path that does the vote rewrite of R4. The cost is ~one approval sweep (5 s), within the spec's 10 s budget (SC-003).

**Sweep integration**: `claimNextForApproval` (`store.ts:855-879`) extends its claim query from `poll_state = 'AWAITING APPROVAL' AND poll_approval_timestamp IS NULL` to also claim `pending_update IS NOT NULL AND poll_approval_timestamp IS NULL`. The two pools are disjoint (a pending update only exists on a poll that stayed in its own state), so the existing claim/attempt columns (`poll_approval_timestamp`, `poll_acceptability_screening_attempts`) are reused unchanged, as is `recoverCrashedApprovalClaim` (`store.ts:841-853`). The sweep screens the poll's content *as it would be after the pending update* (pending title/subtitle/labels overlaid on the stored ones). Outcomes:
- **Approved**: apply the pending fields in one transaction (R4 for deletions), clear `pending_update` and `pending_rejection_reason`, clear the claim fields. `pollState` is not written, so `launched_at` is never re-stamped (`store.ts:675-683` stamps only on a state transition to OPEN) and a closed-meanwhile poll stays closed (clarification Q2, FR-025).
- **Rejected**: clear `pending_update`, set `pending_rejection_reason` to the verdict, clear the claim fields. The poll row is otherwise untouched.
- **Timeout/attempts**: identical to today's behaviour for `AWAITING APPROVAL` (clear the claim timestamp, bump the reason; exhaustion rejects), applied to the pending pool.

**Alternatives considered**: (a) keep `AWAITING APPROVAL` but make that state listable and votable — touches every reader of `pollState` and conflates two meanings of one state; (b) a separate `pending_updates` table — a second entity and a join for what is strictly 0-or-1 per poll (FR-006); (c) apply at save and revert on rejection (NC1's option B) — explicitly not accepted.

## R3. Choices change by id on a voted poll (UA1, AM4)

**Decision**: A new service function `mergeChoices(poll, labels, colors, config)` beside `replaceChoices` (`service.ts:936-972`). It validates exactly as `replaceChoices` does — min/max count (`service.ts:951-953`), `CHOICE_LABEL_MAX = 100` (`service.ts:33`), unique trimmed labels (exact match, `service.ts:957-959`) — then matches each submitted line to the stored choices by exact label after trimming: a match keeps that choice's `id`, `label` and `position`; an unmatched line becomes an addition appended after the highest existing position with a freshly minted `randomUUID()` id; a stored choice with no matching line is a deletion. It returns `{ choices, deletedIds }`. Colors pair with labels positionally as today (`checkedColors`), so a surviving choice keeps or updates its colour and an added one is Automatic unless the Colors step set one (UA4 keeps every existing Automatic bar in place because positions don't change).

**Rationale**: `replaceChoices` reissues every id (`randomUUID()` per choice, `service.ts:964-969`) and its own comments say it is safe only pre-vote; `votes.choice_ids`, `cnt:<pid>`, `vote_history` and `line_graph_tally` are all keyed by those ids. The exact-label match is the accepted AM4 rule and is the same matching the populate script already uses. The whole-list `replaceChoices` path stays reserved for never-voted polls (UA1).

**Alternatives considered**: position-based rename detection (AM4 option B) — rejected in requirements.

## R4. Applying a deletion: vote rewrite, counters, tally (NC2)

**Decision**: When the sweep applies a pending update whose `deletedIds` is non-empty, inside the apply transaction it: (1) rewrites votes — for each deleted id, `UPDATE votes SET choice_ids = array_remove(choice_ids, <id>) WHERE poll_id = <pid> AND choice_ids @> ARRAY[<id>]` — collecting the affected emails; (2) calls `rebuildLineGraphTally(trx, pid)` (`src/polls/lineGraphTally.ts:152-158`, already transactional: deletes the poll's tally and selection rows and refills from `vote_history`); (3) writes the new `choices` and clears `pending_update`. After commit it runs `reconcile(deps, [pid])` (`src/polls/counters.ts:147-185`, which recomputes `total` and per-choice counts from `votes` and zeroes stale hash fields) and `forgetTabs` for the affected voters (`src/refresh/tabVersions.ts:37-46`).

**Rationale**: An emptied vote (`choice_ids = '{}'`) already means "not voted" everywhere: `computeResults` counts `totalVoted` as rows with non-empty `choiceIds` (`service.ts:304-320`), empty rows are the existing invitee-placeholder convention, and — decisive for NC2's "may vote again" — the consumer's Final-vote upsert writes a new vote **only when the existing `choice_ids` is empty** (`src/votes/consumer.ts:85-104`), so a Final voter whose vote was emptied can re-vote with no further change. `vote_history` is append-only and keeps the deleted ids (history is truth); the graph builder skips non-current ids when serving. `reconcile` is the existing operator-grade recount and already zeroes stale counter fields (`counters.ts:179`).

**`user_polls`**: the `voted` relation of an emptied voter is kept — it records participation, the Your Votes tab then shows the poll without a selection and the card lets them vote again. Removing it would be extra work for no requirement.

**Alternatives considered**: keeping stale ids in votes (NC2 option B) — rejected in requirements; filtering at read time — leaves `totalVoted` wrong and Final voters locked out.

## R5. Relaxing the freezes (points 2–4, AM2, UA6)

**Decision**: In `validatePollFields` (`service.ts:481-675`), for an ever-voted poll: `pollSharingMode` becomes changeable (both directions) when the poll is Private; `choiceMode` accepts exactly the `Single-Choice Poll → Multiple-Choice Poll` direction and refuses the reverse with 409; `voteMutability` becomes changeable both ways. `pollVisibility`, `voteAnonymity` and `keywords` stay frozen (`service.ts:532-534, 552-554, 562-564`). `UPDATE_FIELDS` (`pollsApi.ts:515-518`) gains `labels`, `choiceMode`, `voteMutability` and `pollSharingMode`. All freezes remain keyed on `hasEverVoted` (AM2): an open never-voted poll keeps today's full EDIT-mode editor and its existing `/publish` → `AWAITING APPROVAL` flow.

**Rationale**: Existing votes are rows in `votes` keyed by choice id and email; none of the three switches touches them (UA6 "kept exactly as cast"). Dynamic↔Final is enforced per-vote at write time (consumer upsert rule), so switching it changes only future writes. Single→Multiple only widens what `validateVoteChoicesAndState` accepts (`service.ts:451-453`). The sharing-mode switch changes only the access checks, which are evaluated live (R9).

## R6. The vote-counts snapshot in the edit-session response (UA3)

**Decision**: The edit-session grant (`pollsApi.ts:288`) adds `choiceCounts: Record<string, number>` (choice id → count) read from the live counters: `rebuildIfMissing` then parse `cnt:<pid>` (`counters.ts:29-37, 75-88`) — the same source the voter tabs read. The card stores it on `session` and uses it only for the deletion confirmation (AM5).

**Rationale**: `buildAdminPollDetail` strips `currentVotes` (`pollsApi.ts:226-234`) and the admin card today has no per-choice counts at all (its only counts are the totals panel, `adminCard.js:2209-2220`). The live counters are one cache read, already consistent with what voters see, and the snapshot is taken exactly at edit-mode entry as UA3 requires.

## R7. The client merge and the deletion confirmation (IN1, AM3, AM5)

**Decision**: The Choices step keeps its textarea, Paste choices button and help text in every state (IN1). In UPDATE mode the step is unlocked (today `lockStep(3)` disables `.m3-field-input` and the paste button, `adminCard.js:1772`). The merge diff is computed against `session.poll.choices` (already delivered by the grant and stored at `adminCard.js:2700-2719`) by the same exact-trimmed-label rule as the server. The confirmation fires when the Choices section is being left with voted deletions pending — the three exits are `goToStep` away from step 3 (`adminCard.js:685-694` already intercepts it for duplicates), Next (`adminCard.js:909`), and Save changes — and it is a new `askToDeleteChoices(deletions)` dialog cloned from the `askToDiscard` pattern (`adminCard.js:62-108`: shared-Promise `role=alertdialog`, Escape/scrim = cancel, focus management), listing each voted deletion as "label — N votes" from the R6 snapshot. Confirm proceeds; Cancel restores `wizard.choicesText` to the session-entry text (whole-section revert, AM3) and keeps focus in the step. Deletions with zero votes never prompt (AM5). A confirmed set is remembered so the prompt does not re-fire for the same unchanged deletions on every exit.

**Rationale**: Reuses the one existing modal confirmation pattern (its CSS is already on admin.html via discard-dialog-m3.css / tabs-modal-m3.css), the existing blur plumbing (`wireChoicesBox` hooks, `adminCard.js:2578-2622`) and the existing duplicate-block precedent for refusing to leave the step. Client validation needs no new code: the 100-char cap and max-count already run in `sanitizeChoicesText` (an existing poll already uses `CHOICE_LABEL_MAX` = 100, `adminCard.js:1283-1284`), duplicates are flagged (`adminCard.js:236-245`) and block leaving, and the minimum bound is `choicesProblem()` (`adminCard.js:589-592`) — UA8's "disabled below the minimum" is the existing disabled Save with that reason (`adminCard.js:1876-1882`).

## R8. Card status for pending and rejected changes (FR-024, Q1)

**Decision**: `adminListRow` gains `pendingUpdate: boolean` and `pendingRejectionReason` (`pollsApi.ts:682-722`). While `pending_update` is set, `editModeFor` (`service.ts:209-226`) answers `INELIGIBLE` with reason `PENDING_REVIEW` and message "Changes are being reviewed. Try again shortly." — the same pattern as `AWAITING APPROVAL` today — so the editor cannot be re-entered and a second save is structurally impossible (FR-006 also enforced in `/publish` with `409 { code: "PENDING_REVIEW" }` as the backstop). The read-only card header shows the status detail "changes pending review" beside the state (the `card-state-detail` slot, `adminCard.js:143-147, 2104-2110`), and shows `pendingRejectionReason` as "changes rejected: <reason>" when set; the admin list's existing 5 s auto-refresh (`adminList.js:494-496`) picks up the resolution, which satisfies "approval clears the status quietly". A later successful save clears `pending_rejection_reason`.

**Rationale**: The card already renders per-state details in exactly this slot (AWAITING APPROVAL queue time, REJECTED reason), the refresh loop already exists, and refusing the editor is simpler and safer than letting the creator stage edits that the pending apply would race.

## R9. The sharing-mode switch's effects (UA5)

**Decision**: No new enforcement code. Switching is a field change applied at Save (R2's immediate part); every access decision already reads the live poll: voting via `assertEligible`'s invitation check (`src/votes/votePath.ts:104-140` over the `invite:<pid>` roster cache), viewing via `decideSharedLink` (`src/polls/sharedLink.ts:55-80`) and `reaches` (`src/polls/access.ts:49-53`), watching via `mayWatch` (`access.ts:59-70`), results via `mayViewResults` (`access.ts:79-86`) — all keyed on `isInvitationOnly` (`store.ts:46-49`). Invitation rows are not touched by the switch (`writeInvitations` preserves rows, `store.ts:531-556`), so the record stays as history when switching to Anyone-with-the-Link and reconnects voters by email key when switching back (adoption already runs at sign-in, the shared link and the tab: `invitations.ts:344-394`). Votes and `user_polls` rows are untouched (UA5). One check in implementation: `validatePollFields`' invitation-only placeholder handling of `currentVotes` (`service.ts:602-634`) runs when the roster lists are sent; the mode switch alone must not rewrite votes.

## R10. Schedule and state interplay (FR-025, Q2)

**Decision**: The pending apply writes content fields only, never `pollState`. The date-check sweep is untouched: it already ignores EDITING and only reconciles WAITING TO OPEN/OPEN/CLOSED against the schedule (`store.ts:810-823`). A poll that closes while its pending update is under review therefore gets the approved content and stays CLOSED. Because the immediate part of a save no longer passes through `AWAITING APPROVAL`, approval's `launched_at` re-stamp (`store.ts:675-683`) no longer fires for voted-poll saves at all — the Technical Debt item about old polls jumping to the top of Newest is retired for this path.

## R11. The second save (FR-006, assumption)

**Decision**: Refused at two layers: `editModeFor` ineligibility while `pending_update` is set (R8) prevents opening the editor at all, and `/publish` answers `409 { error: "Changes are already being reviewed. Try again shortly.", code: "PENDING_REVIEW" }` if a stale card still posts. No replace-the-pending-set semantics (documented spec assumption).

Multiple→Single refusal), `tests/client-admin-wizard.test.ts` (unlocked steps in UPDATE mode, merge confirmation dialog, Cancel revert, payloads), and `tests/openapi-contract.test.ts` for the contract changes.
